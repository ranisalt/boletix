# TSE QR signature verification: Ed521 and P-521

This note matches the TSE Python example in **“QR Code no Boletim de Urna: Manual para Criação de Aplicativo de Leitura,” §1.6.3.1, pp. 22–23**. Inputs below are the decoded bytes, not their hexadecimal text:

- `msg`: bytes decoded from the final QR's `HASH` field (`dados_hash_qr` in Python).
- Ed521 `pubKey`: the raw public-key bytes from the certificate SPKI BIT STRING; Ed521 compressed-point encoding, 66 bytes.
- Ed521 `sig`: bytes decoded from `ASSI`; raw `R || S`, 132 bytes.
- P-521 `pubKey`: SEC1-encoded EC point from SPKI BIT STRING (usually uncompressed, `04 || X || Y`, 133 bytes).
- P-521 `sig`: ASN.1 DER ECDSA signature, as returned/accepted by ECPy's default `ECDSA()` formatter.

The TSE manual hashes `dados_hash_qr` with SHA-512 before calling either verifier. ECPy's ECDSA verifier treats its `msg` argument as an already-computed digest: it converts those bytes to an integer and truncates only if longer than the curve size; it does not hash them again. ECPy's EdDSA verifier instead incorporates its `msg` into the EdDSA SHAKE challenge.

## Ed521 facts and Noble support

ECPy at the exact TSE-pinned commit defines Ed521 as the twisted Edwards curve `a*x² + y² = 1 + d*x²*y²` over `p = 2^521 - 1`, with `a=1`, `d` as below, subgroup order `n`, cofactor `h=4`, and generator `(Gx,Gy)`. Its `size` is 521 bits and its coordinate encoding is 66 bytes. Point encoding is little-endian `y` with the parity of `x` in the top bit of the last byte. ECPy's EDDSA formatter encodes the point `R` and scalar `S` as two 66-byte little-endian chunks, so the signature is 132-byte `R || S`.

The Ed521 SHAKE inputs are:

- challenge/nonce: `SHAKE256("SigEd521" || 00 || 00 || prefix || message, 132)`
- challenge scalar: `SHAKE256("SigEd521" || 00 || 00 || R || A || message, 132)`

That 10-byte leading domain is `dom5(phflag=0, context="")`. This is **PureEdDSA**, not Ed521ph. The TSE wrapper's separate `SHA512(dados_hash_qr)` step is still required; EdDSA itself does not prehash its message in this mode.

`@noble/curves` **2.2.0** (the latest npm release checked) has no Ed521 export or built-in parameter set. Its `ed448` export is RFC 8032 Ed448-Goldilocks, not E-521. It does expose generic `edwards()` and `eddsa()` APIs for custom curves. One E-521-specific trap: the subgroup order is 519 bits (65 bytes at its natural width), while `p` and the EdDSA wire coordinate/scalar widths are 521 bits / 66 bytes. Noble documents that some code assumes `Fp.BYTES === Fn.BYTES`; configure `Fn` with `BITS: 521` so the scalar field also serializes to 66 bytes. Without this override, custom E-521 construction/encoding is incorrect (the unadjusted constructor fails on the base point in the checked release).

## Copy-paste TypeScript

Requires `@noble/curves@2.2.0` and its matching `@noble/hashes@2.2.0` dependency. The helpers take `msg` as the decoded `HASH` bytes and perform the TSE SHA-512 step internally. Catching parser/point errors makes malformed inputs return `false`.

```ts
import { eddsa, edwards, type EdwardsOpts } from '@noble/curves/abstract/edwards.js';
import { Field } from '@noble/curves/abstract/modular.js';
import { p521 } from '@noble/curves/nist.js';
import { sha512 } from '@noble/hashes/sha2.js';
import { shake256 } from '@noble/hashes/sha3.js';

const ED521_CURVE: EdwardsOpts = {
  p: BigInt('0x1ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff'),
  n: BigInt('0x7ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffd15b6c64746fc85f736b8af5e7ec53f04fbd8c4569a8f1f4540ea2435f5180d6b'),
  h: 4n,
  a: 1n,
  d: BigInt('0x1fffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffa4331'),
  Gx: BigInt('0x752cb45c48648b189df90cb2296b2878a3bfd9f42fc6c818ec8bf3c9c0c6203913f6ecc5ccc72434b1ae949d568fc99c6059d0fb13364838aa302a940a2f19ba6c'),
  Gy: 12n,
};

const shake256_132 = Object.assign(
  (data: Uint8Array) => shake256(data, { dkLen: 132 }),
  { outputLen: 132 }
);
const ed521Point = edwards(ED521_CURVE, {
  FpFnLE: true,
  // The E-521 subgroup order is 519 bits, but EdDSA encodes S in 66 bytes.
  Fn: Field(ED521_CURVE.n, { BITS: 521, isLE: true }),
});
const ED521_DOMAIN = new TextEncoder().encode('SigEd521\0\0');
const ed521 = eddsa(ed521Point, shake256_132, {
  // Noble calls domain() on both nonce and challenge hash inputs.
  domain: (data: Uint8Array, _context: Uint8Array, phflag: boolean): Uint8Array => {
    if (phflag) throw new Error('TSE QR signatures use PureEdDSA (phflag=0)');
    const prefixed = new Uint8Array(ED521_DOMAIN.length + data.length);
    prefixed.set(ED521_DOMAIN);
    prefixed.set(data, ED521_DOMAIN.length);
    return prefixed;
  },
});

/** msg is the decoded bytes of the QR HASH field, not its hex text. */
export function verifyEd521(pubKey: Uint8Array, msg: Uint8Array, sig: Uint8Array): boolean {
  if (pubKey.length !== 66 || sig.length !== 132) return false;
  try {
    return ed521.verify(sig, sha512(msg), pubKey);
  } catch {
    return false;
  }
}

/** pubKey is the SEC1 point from SPKI; sig is the ECPy DER signature. */
export function verifyP521(pubKey: Uint8Array, msg: Uint8Array, sig: Uint8Array): boolean {
  try {
    return p521.verify(sig, sha512(msg), pubKey, {
      prehash: false,
      format: 'der',
      lowS: false,
    });
  } catch {
    return false;
  }
}
```

## ECDSA P-521: the prehash choice

The snippet explicitly computes `D = SHA512(msg)` and then passes `D` to Noble with **`prehash: false`**. This exactly mirrors Python's `ECDSA.verify(SHA512(dados_hash_qr), sig, pubkey)`: ECPy expects a digest and does not hash it again. P-521's Noble default is `prehash: true` and hash function SHA-512. Therefore, either of these is equivalent for the helper's raw `HASH` input:

```ts
p521.verify(derSig, sha512(msg), pubKey, { prehash: false, format: 'der', lowS: false });
// or, pass the un-hashed HASH-field bytes so Noble performs SHA-512 once:
p521.verify(derSig, msg, pubKey, { prehash: true, format: 'der', lowS: false });
```

Do **not** pass `SHA512(msg)` with Noble's default `prehash: true`: that computes SHA-512 twice. `lowS: false` matters for parity with ECPy, which checks `0 < r,s < n` but does not enforce low-S. `format: 'der'` is required because ECPy `ECDSA()` defaults to DER; Noble's default ECDSA signature format is compact `r || s`.

WebCrypto `SubtleCrypto.verify` accepts the original signed data and an ECDSA hash algorithm, with no prehash toggle. To match TSE, give WebCrypto the raw decoded `HASH` bytes and set `{name:'ECDSA', hash:'SHA-512'}`; it hashes once internally. If you pass the already-hashed 64-byte `D`, it hashes `D` again. Also convert ECPy's DER signature to WebCrypto's fixed-width P1363 `r || s` encoding before calling `verify`.

## Compatibility caveat

ECPy's EdDSA verifier checks the uncofactored equation `R + hA == S*B`; Noble's generic EdDSA verifier checks the cofactored RFC-style equation. They agree for normal Ed521 signatures and public keys in the prime-order subgroup (the TSE key/signature generation path), as confirmed with ECPy's published Ed521 vector below. For deliberately malformed/off-subgroup encodings, acceptance may differ; this helper is for TSE-generated, certificate-validated keys and signatures.

## Verification performed

Using a scratch-only install of `@noble/curves@2.2.0` / `@noble/hashes@2.2.0` (nothing installed in the repo), the TypeScript compiled in strict mode and the executable smoke test passed:

- ECPy's published Ed521 public key/signature/message vector verifies through the custom Noble Ed521 instance.
- The TSE-style Ed521 wrapper verifies a signature over `SHA512(HASH-bytes)`.
- The P-521 wrapper verifies a DER signature over the same one-time SHA-512 prehash with `prehash:false`.
